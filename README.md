# CrossApp

Наскрізний проєкт з крос-платформного програмування для обліку товарів і складських залишків. Заплановані сутності: `Product`, `StockBatch`, `Warehouse`, `Movement`.

## Середовище та режими роботи

Проєкт використовує .NET SDK 10. Приклади команд наведено відносно каталогу `CrossApp`.

```bash
dotnet build
dotnet run --project src/Cli
```

Без аргументів CLI показує `report-top` лабораторної 7 зі сховищем у пам’яті. Звіт за даними файлового сховища:

```bash
dotnet run --project src/Cli -- --file
```

Попереднє демо операцій каталогу та подій запускається явно (воно змінює дані):

```bash
dotnet run --project src/Cli -- --demo-catalog
dotnet run --project src/Cli -- --demo-catalog --file --cache
```

Режим імпорту з лабораторної 3 приймає шлях до файлу:

```bash
dotnet run --project src/Cli -- data/correct_sample.csv
dotnet run --project src/Cli -- data/sample.json
dotnet run --project src/Cli -- data/sample.mixed.csv
```

Демонстрація доменної моделі з лабораторної 4 запускається окремо:

```bash
dotnet run --project src/Cli -- --demo-domain
```

## Структура проєкту

```text
CrossApp/
├── CrossApp.sln
├── data/                     # приклади CSV і JSON
└── src/
    ├── Core/                 # дані, імпорт і доменна модель
    │   ├── Dto/              # ProductDto, WarehouseDto, ImportResult<T>
    │   ├── Import/           # імпортери та перетворення DTO на Product
    │   ├── Domain/           # Product, Warehouse, Order та сервіс надходження
    │   ├── Abstractions/     # ICatalogStore
    │   ├── Storage/          # InMemoryCatalogStore, FileCatalogStore
    │   ├── Services/         # CatalogService
    │   ├── SampleData.cs     # 18 демонстраційних товарів
    │   └── EnvironmentInfo.cs
    └── Cli/
        └── Program.cs        # ручний DI, демонстрації та імпорт
```

`Cli` посилається на `Core`. DTO переносять дані; імпортери читають файли; `Domain` містить сутності з правилами; `Storage` зберігає товари, а `Services` виконує операції через інтерфейс сховища.

## Лабораторна 1 — структура та публікація

Створено рішення з бібліотекою `Core` і консольним застосунком `Cli`. Проєкт розроблявся на Windows 11 x64 із .NET SDK 10.0.

Для `win-x64` перевірено два режими публікації:

```bash
dotnet publish src/Cli -c Release -r win-x64 --self-contained false -o publish/win-x64-fd
dotnet publish src/Cli -c Release -r win-x64 --self-contained true -o publish/win-x64-sc
```

| Режим               | Що містить                                | Чи потрібен .NET Runtime на іншій машині |
| :------------------ | :---------------------------------------- | :--------------------------------------- |
| Framework-dependent | Застосунок і його залежності              | Так, сумісний .NET 10 Runtime            |
| Self-contained      | Застосунок разом із середовищем виконання | Ні                                       |

Self-contained збірка більша та прив'язана до конкретної ОС й архітектури. У вимірах лабораторної 1 розміри self-contained публікацій становили **70,50 МБ** для `win-x64` і **70,51 МБ** для `linux-x64`. В інших вимірах публікації отримано приблизно **76,67 МБ** для `win-x64` self-contained, **0,19 МБ** для framework-dependent і **78,80 МБ** для `linux-x64` self-contained; це результати різних збірок, а не одного експерименту.

Додатковий режим `--json` належав до версії лабораторної 1. Поточні команди звітів описано в розділі лабораторної 7 нижче; попередні демонстрації та імпорт також доступні.

## Лабораторна 2 — режими збірки та кілька версій .NET

Перевірено додаткові параметри публікації `win-x64`:

| Параметри                                          | Результат виміру                        |
| :------------------------------------------------- | :-------------------------------------- |
| `-p:PublishSingleFile=true`                        | Один файл `Cli.exe`, приблизно 70,12 МБ |
| `-p:PublishSingleFile=true -p:PublishTrimmed=true` | Один файл `Cli.exe`, 12,35 МБ           |

`PublishTrimmed` прибирає невикористаний код. Для застосунків із рефлексією або динамічною JSON-десеріалізацією цей режим потребує окремої перевірки. Наведені розміри — результати лабораторної 2, а не гарантія для поточного коду.

Бібліотека `Core` збирається для `net8.0` і `net10.0`:

```xml
<TargetFrameworks>net8.0;net10.0</TargetFrameworks>
```

В `EnvironmentInfo.cs` використано умовну компіляцію `#if NET10_0_OR_GREATER`, яка додає `BuildNote`. Окрема збірка бібліотеки виконується командою:

```bash
dotnet build src/Core/Core.csproj
```

## Лабораторна 3 — імпорт складських даних

Додано `ProductDto`, `WarehouseDto`, спільний тип `WarehouseEntryDto` та `ImportResult<T>`. Імпортери повертають коректні записи й окремий список помилок, не зупиняючи обробку через один пошкоджений рядок.

### CSV із товарами

Файл має кодування UTF-8, роздільник `;` і колонки `id;sku;name;unit;quantity`. Заголовок необов'язковий.

```csv
id;sku;name;unit;quantity
P-001;SKU-001;Цемент М400 25кг;шт;120
P-002;SKU-002;Пісок будівельний;т;18
```

Порожні рядки та рядки-коментарі з `#` пропускаються. Неправильна кількість колонок, порожні обов'язкові поля, нечислова або від'ємна кількість потрапляють до списку помилок із номером рядка.

```text
Завантажено записів: 10
Пропущено рядків: 3
  ! рядок 12: очікую 5 колонок, отримав 4
  ! рядок 13: кількість 'багато' не є невід'ємним цілим числом
  ! рядок 14: ідентифікатор, SKU, назва або одиниця вимірювання порожні
```

### Додаткові формати

- **JSON:** `ProductJsonImporter` читає масив товарів через `System.Text.Json`. Назви властивостей зіставляються без урахування регістру. Помилки окремих елементів збираються в `Errors`; синтаксично зламаний JSON дає помилку всього документа.
- **Змішаний CSV:** файл із суфіксом `.mixed.csv` містить товари (`P;id;sku;name;unit;quantity`) і склади (`W;id;name;location`). `MixedWarehouseCsvImporter` розпізнає типи через `switch expression` і list patterns.
- **Статистика:** після імпорту CLI показує кількість оброблених, прийнятих і пропущених записів та відсоток помилок. Заголовки, порожні рядки й коментарі не враховуються.

```text
Статистика: усього 13, прийнято 10, пропущено 3, помилок 23,1%
```

## Лабораторна 4 — доменна модель

`ProductDto` з лабораторної 3 залишається форматом передачі даних. Клас `Core.Domain.Product` відповідає за коректний стан товару. Товар можна створити лише через `Product.Create(...)`: конструктор приватний, а властивості не мають публічних сетерів.

### Інваріанти товару

| Правило                                   | Де перевіряється           | Виняток                       |
| :---------------------------------------- | :------------------------- | :---------------------------- |
| `Id`, `Sku`, `Name`, `Unit` не порожні    | `Create`                   | `ArgumentException`           |
| Початковий залишок не від'ємний           | `Create`                   | `ArgumentOutOfRangeException` |
| Кількість приходу й видачі більша за нуль | `RegisterArrival`, `Issue` | `ArgumentOutOfRangeException` |
| Видача не перевищує залишок               | `Issue`                    | `InvalidOperationException`   |
| Прихід не переповнює `int`                | `RegisterArrival`          | `InvalidOperationException`   |

`Create` очищає обов'язкові рядки від пробілів по краях і приводить `Sku` до верхнього регістру. Необов'язкове `Note` зберігається в сутності. Усі операції перевіряють умови **до** зміни залишку, тому після винятку стан товару не змінюється.

`ToDto()` повертає поточні дані товару, а `FromDto(dto)` відновлює сутність через `Create(...)` із тими самими перевірками. Таким чином, некоректний DTO не може створити доменний об'єкт.

### Демонстрація в CLI

Режим `--demo-domain` показує успішний прихід і видачу, перетворення `Product → ProductDto → Product`, а потім спроби порушити інваріанти:

```text
=== Сценарій 1: успішні операції ===
Початковий залишок SKU-001: 100 шт
Після приходу 50 і видачі 30: 120 шт
Product → DTO → Product: SKU-001, залишок 120 шт, примітка: Демонстраційний товар

=== Сценарій 2: порушення інваріантів ===
видача більша за залишок: InvalidOperationException — Не можна видати 1000 одиниць товару SKU-001: залишок становить 120
нульова кількість приходу: ArgumentOutOfRangeException — Кількість приходу має бути більшою за нуль (Parameter 'amount') Actual value was 0.
порожній SKU: ArgumentException — SKU товару не може бути порожнім (Parameter 'sku')
від'ємний початковий залишок: ArgumentOutOfRangeException — Початковий залишок не може бути від'ємним (Parameter 'quantity') Actual value was -5.
некоректний DTO: ArgumentOutOfRangeException — Початковий залишок не може бути від'ємним (Parameter 'quantity') Actual value was -1.
Залишок після відмов: 120 шт (до них: 120 шт)
```

CLI показує тип і повідомлення винятку. Звичайні команди імпорту файлів продовжують працювати окремо від демонстрації.

### Додаткове завдання — результат імпорту в доменній моделі

`ProductDomainConverter.Convert(...)` приймає `ImportResult<ProductDto>` і повертає `ImportResult<Product>`. Кожен DTO проходить через `Product.FromDto`, а отже й через перевірки `Product.Create`. Коректні товари потрапляють до `Items`; DTO, що порушують інваріанти, пропускаються, а причина додається до `Errors` із порядковим номером DTO та його `Id`. Номер DTO означає його позицію в `Items` вхідного результату, а не номер рядка початкового файлу.

Помилки, які вже повернув імпортер, зберігаються в результаті. Тому один виклик дає і придатні для роботи доменні товари, і повний список відомих помилок. Режим `--demo-domain` показує це у третьому сценарії на прикладі трьох DTO, один з яких має від'ємний залишок, і однієї ранішої помилки імпорту:

```text
=== Сценарій 3: DTO → доменні товари ===
DTO на вході: 3
Доменних товарів: 2
  + P-010: SKU-010, 15 т
  + P-012: SKU-012, 8 т
Помилок (імпорт + домен): 2
  ! рядок 7: кількість 'багато' не є цілим числом
  ! DTO №2 (Id: P-011): Початковий залишок не може бути від'ємним ...
```

### Додаткове завдання — правило для двох сутностей

`Warehouse` зберігає місткість, одиницю вимірювання та зайняте місце. `WarehouseReceivingService.Receive(warehouse, product, amount)` оформлює надходження товару. Сервіс перевіряє, що одиниця товару відповідає одиниці місткості складу, місця вистачає і залишок товару не переповниться. Лише після всіх перевірок він збільшує залишок `Product` і зайняте місце `Warehouse`. Таке правило розміщене в сервісі, бо для рішення потрібен стан **обох** сутностей; окремий `Product` не знає місткості складу, а окремий `Warehouse` не знає одиниці й залишку товару.

У четвертому сценарії `--demo-domain` надходження 6 шт проходить успішно, а спроби додати ще 5 шт на склад місткістю 10 шт або прийняти товар у тоннах завершуються відмовою. Після обох відмов стан товару й складу лишається таким самим.

### Додаткове завдання — стани замовлення

`OrderStatus` задає три стани: `Draft`, `Confirmed`, `Cancelled`. Нове `Order` починає зі стану `Draft`. Метод `ChangeStatus` використовує `switch expression` для двох дозволених переходів: `Draft → Confirmed` і `Draft → Cancelled`. Стани `Confirmed` і `Cancelled` кінцеві; повторний або будь-який інший перехід спричиняє `InvalidOperationException`. У разі відмови `Status` не змінюється, бо присвоєння відбувається лише після успішного обчислення виразу.

П’ятий сценарій `--demo-domain` показує обидва дозволені переходи та спроби змінити кінцеві стани. Статус має приватний сетер, тому код поза `Order` не може обійти ці правила прямим присвоєнням.

## Лабораторна 5 — сервісний шар і два сховища

`ICatalogStore` визначає `List`, `GetById`, `Add`, `Update`, `Remove`. `InMemoryCatalogStore` зберігає товари в пам’яті, а `FileCatalogStore` завантажує JSON при першому зверненні та записує його після змін. Пошук і перевірка дублів ідентифікатора не залежать від регістру. `Update` в обох реалізаціях відхиляє відсутній товар.

`CatalogService` отримує інтерфейс сховища через конструктор. Операції `Add`, `Receive`, `Issue` використовують правила сутності `Product`; `All` і `Find` читають каталог. Конкретне сховище створює `Cli.StoreFactory`; `Program.cs` передає його сервісу. DI-контейнер не підключено.

Без аргументів запускається сховище в пам’яті з 18 початковими товарами. Сценарій додає 50 м кабелю, приймає 25 м, видає 10 м, знаходить товар та показує список. При повторному запуску внесені зміни зникають, початкові товари створюються заново.

З `--file` каталог починається з даних попереднього запуску або порожнього набору, якщо файла немає. Кожен запуск додає новий товар із новим GUID. Файл: `data/catalog.json` відносно `AppContext.BaseDirectory`; у Debug/net10.0 це `src/Cli/bin/Debug/net10.0/data/catalog.json`. CLI друкує точний шлях. Товари зберігаються як масив `ProductDto`; примітки також зберігаються.

Сценарій відмови: надходження для `missing-id`, повідомлення `Помилка: Немає товару з id=missing-id.`. Помилки читання/запису та некоректний JSON повідомляються у CLI з кодом завершення 1.

### Додаткове завдання 1 — кешування

`CachingCatalogStore(ICatalogStore inner)` обгортає сховище і зберігає результати `List` та `GetById`, включно з відсутніми товарами. `Add`, `Update`, `Remove` очищають обидва кеші перед делегуванням. Прапорець `--cache` працює з пам’яттю або файлом:

```powershell
dotnet run --project src/Cli -- --demo-catalog --cache
dotnet run --project src/Cli -- --demo-catalog --file --cache
```

Усі зміни мають проходити через декоратор. Він не відстежує зміни файла з іншого процесу, а кешовані `Product` залишаються змінюваними сутностями. Файлове сховище вже має власний кеш, тому обгортка тут передусім демонструє патерн декоратора.

### Додаткове завдання 2 — пошук із власною умовою

`CatalogService.Search(Func<Product, bool> predicate)` повертає `IReadOnlyList<Product>`. Кожен товар проходить передану умову; `true` включає його до результату. Приклади: `service.Search(p => p.Quantity < 10)` або `service.Search(p => p.Unit == "м" && p.Name.Contains("Кабель"))`. `null` замість функції відхиляється. CLI показує обидва пошуки після операцій із товаром.

Пошук виконується у сервісі над `_store.List()` і працює з усіма реалізаціями без розширення `ICatalogStore`. Результат — окрема колекція лише для читання з посиланнями на доменні товари.

### Додаткове завдання 3 — фабрика сховищ

`Cli.StoreFactory.Create(string[] args)` повертає `ICatalogStore`: пам’ять за замовчуванням, файл із `--file`, обгортку `CachingCatalogStore` із `--cache`. Обидва прапорці можна поєднувати у будь-якому порядку. Повторні та невідомі прапорці відхиляються. `IsCatalogMode` відокремлює каталог від старих режимів імпорту й доменної демонстрації. `StoreFactory.DataPath` є єдиним джерелом шляху JSON.

`Program.cs` тепер викликає фабрику й передає результат у `CatalogService`; він залишається composition root. Порівняння: пряме створення у Program коротше для двох реалізацій, фабрика зосереджує вибір, перевірку аргументів та декорування в одному місці. Фабрика належить Cli, оскільки знає прапорці запуску. Контейнер DI не використовується.

## Лабораторна 6 — події каталогу та делегати

`Core.Events` містить `CatalogChangeKind` і `CatalogChangedEventArgs`. `CatalogService.Changed` сповіщає про успішні `Add`, `Receive` та `Issue`; дельта видачі від'ємна. Подія піднімається після запису в сховище, а помилка валідації чи пошуку не створює повідомлення. `Removed` залишено серед типів змін для майбутнього методу видалення.

У `Cli` локальний обробник підписується на `Changed`, друкує рядок події та додає його до `logs/app.log`. Другий обробник-лямбда збільшує локальний лічильник. Демонстрація показує відписку від логера: зміна залишку продовжується, але рядок події більше не друкується й не записується у файл; лічильник другого підписника змінюється. Сценарій від'ємного приходу демонструє відмову без події. Пошук використовує `Search(Func<Product, bool>)`.

### Додаткове завдання 1 — передавання сповіщувачів через інтерфейс

`INotificationSink` задає спільний метод `Notify`. `ConsoleSink` та `FileSink` реалізують його в `Cli`; composition root створює ці компоненти та передає їх до `CatalogService` як список інтерфейсів. Окрема демонстрація запускається командою `dotnet run --project src/Cli -- --demo-sinks`; вона пише у консоль і `logs/app-sinks.log`. Демонстрація подій запускається через `--demo-catalog`, а `--demo-sinks` показує ін'єкцію залежностей для порівняння.

### Додаткове завдання 2 — звіт про пропущені рядки через Action

`ProductCsvImporter.Load` приймає необов'язковий `Action<string> reportSkipped`. Для кожного некоректного рядка імпортер додає текст помилки до `ImportResult.Errors` і викликає передану дію. `Cli` передає лямбду, яка виводить повідомлення; імпортер не залежить від консолі. Запуск `dotnet run --project src/Cli -- data/sample.csv` показує цей callback на рядках із помилками.

### Додаткове завдання 3 — асинхронний обробник події

Стандартний `EventHandler<TEventArgs>` повертає `void`. Тому асинхронна лямбда на кшталт `async (_, e) => await WriteAsync(e)` стає `async void`: видавець події не може дочекатися її завершення, а виняток з асинхронної частини не повертається до `try/catch`, який викликав подію. Метод або інтерфейс із результатом `Task` дозволяє викликачеві дочекатися завершення асинхронної роботи через `await` і перехопити її винятки. У цій лабораторній обробники лишаються синхронними.

### Додаткове завдання 2 — власний метод розширення TopBy

`Core.Extensions.EnumerableExtensions.TopBy<T>` приймає послідовність, Func<T, int> для вибору показника, кількість n і Func<T, string> для другого ключа. Параметр `this IEnumerable<T> source` дозволяє викликати метод як `source.TopBy(...)`. Метод поєднує OrderByDescending, ThenBy з Ordinal та Take; додатковий унікальний ключ забезпечує визначений порядок за однакового показника. Результат відкладений: він виконується при перебиранні або ToList. Нульове n дає порожню послідовність, від'ємне відхиляється; null-аргументи також перевіряються.

Метод використовується у двох звітах:

- `TopByQuantity`: топ товарів за залишком; другий ключ — SKU. Наявна команда report-top зберігає результат.
- `TopByMovementCount`: топ товарів за кількістю переміщень на основі зведених DTO першого додаткового завдання; другий ключ — SKU. Враховуються всі товари, зокрема з нульовою кількістю переміщень, якщо для заповнення топу недостатньо інших.

```bash
dotnet run --project src/Cli -- report-movements-top
```

На демонстраційних даних порядок топ-5: SKU-001 (3 рухи), SKU-008 (2), SKU-002 (1), SKU-005 (1), SKU-003 (0). TopBy працює і з Product, і з MovementSummary: тип T визначається з джерела.

### Додаткове завдання 3 — синтаксис запитів

Звіт `ByUnit`, який запускається через `report-groups`, переписано з використанням синтаксису запитів:

```csharp
var query =
    from g in source.GroupBy(p => p.Unit, StringComparer.OrdinalIgnoreCase)
    select new GroupSummary(g.Key, g.Count(), g.Sum(p => p.Quantity)) into summary
    orderby summary.TotalQuantity descending
    select summary;

return query.ThenBy(g => g.Key, StringComparer.OrdinalIgnoreCase).ToList();
```

Еквівалентний попередній запис ланцюжком методів:

```csharp
return source.GroupBy(p => p.Unit, StringComparer.OrdinalIgnoreCase)
    .Select(g => new GroupSummary(g.Key, g.Count(), g.Sum(p => p.Quantity)))
    .OrderByDescending(g => g.TotalQuantity)
    .ThenBy(g => g.Key, StringComparer.OrdinalIgnoreCase)
    .ToList();
```

`from` задає перебір груп, `select ... into summary` проєктує групу в DTO і продовжує запит уже над DTO, `orderby ... descending` сортує підсумки за спаданням. Компілятор перетворює ці конструкції на стандартні виклики Select та OrderByDescending; це не SQL і не інший механізм виконання.

Запис запитом виразніше називає проміжний результат summary та відокремлює проєкцію від сортування. Ланцюжок методів коротший і зручніший там, де потрібні власні comparer або Take. Тут GroupBy та ThenBy залишено методами, оскільки синтаксис `group ... by` і `orderby` не має параметра comparer: так збережено об’єднання «шт»/«ШТ», початкове написання ключа та другий ключ сортування без урахування регістру. Обидві форми повертають ті самі DTO, виконуються відкладено до ToList і коректно обробляють порожнє джерело.

### Додаткове завдання 4 — вимірювання через Stopwatch

```bash
dotnet run --project src/Cli -c Release -- report-benchmark
```

Команда окрема: не приймає --file/--cache і не читає каталог. `Core/Reports/ReportBenchmark.Run` генерує 100 000 товарів у пам’яті з Random(7) і залишками від 0 до 999. Порівнюються два варіанти звіту про товари із залишком менше 500:

```csharp
// Без проміжної матеріалізації:
source.Where(p => p.Quantity < 500)
    .OrderBy(p => p.Quantity).ThenBy(p => p.Sku, StringComparer.Ordinal)

// З проміжною матеріалізацією після фільтра:
source.Where(p => p.Quantity < 500).ToList()

Перевіряється кожен прогрівальний і вимірюваний результат.

## Лабораторна 8 — async/await, скасування та unit-тести

Виконано основне завдання та всі чотири додаткові завдання. ICatalogImporter та JsonCatalogImporter підтримують потокове читання JSON через FileStream(useAsync: true) і JsonSerializer.DeserializeAsyncEnumerable. Записи перевіряються й додаються поступово. Обов'язкові поля: id, sku, name, unit, quantity; регістр назв полів неважливий. Старі синхронні імпортери залишені для сценаріїв попередніх лабораторних. Звіти та операції в пам'яті залишаються синхронними.

Команди з каталогу CrossApp:

```powershell
dotnet test
dotnet run --project src/Cli -- import data/lab08-valid.json
dotnet run --project src/Cli -- import data/lab08-valid.json --file
dotnet run --project src/Cli -- import data/lab08-invalid.json
dotnet run --project src/Cli -- import data/lab08-valid.json --timeout-ms=0
```

Без --file імпорт використовує нове порожнє сховище в пам'яті. --file зберігає товари в каталозі StoreFactory.DataPath; повторний імпорт тих самих Id додає 0 записів. Підтримується --cache. Подія Changed виникає лише для нових записів після успішного додавання.

Скасування тривалого імпорту підтримується через Ctrl+C або таймаут --timeout-ms=N. Імпорт короткого файла може завершитися раніше таймауту; --timeout-ms=0 відтворювано демонструє вже скасовану операцію. Код завершення: 0 — успіх, 1 — помилка, 2 — скасування. Токен передається Cli → ImportAsync → StreamAsync → DeserializeAsyncEnumerable і перевіряється перед відкриттям файла та в циклах. Скасування не відкочує вже додані товари.

DomainException позначає бізнес-відмову (наприклад видачу понад залишок) або неправильний запис імпорту з номером запису; початкова помилка валідації зберігається в InnerException. ArgumentOutOfRangeException залишається для від'ємного або нульового аргументу кількості. IOException і JsonException не маскуються як доменні; OperationCanceledException обробляється окремо. Некоректні дані виводяться як «Дані відхилено», скасування — «Імпорт скасовано».

Core.Tests посилається лише на Core. Власні фіксовані дані не залежать від SampleData або data/. Тести перевіряють незмінність стану після відмови, одну подію, доменну відмову, строгий поріг звіту, стабільний порядок топу, скасування до читання й у циклі, передачу токена, повторний імпорт і JSON. Файлові перевірки використовують унікальні тимчасові файли з видаленням у finally. Тести ізольовані: кожна перевірка створює власне сховище та фіксований набір даних.

### Додаткове завдання 1 — потоковий імпорт

ICatalogImporter.StreamAsync повертає IAsyncEnumerable<Product>. JsonCatalogImporter читає елементи кореневого JSON-масиву через JsonSerializer.DeserializeAsyncEnumerable<JsonElement>, перевіряє кожен запис і передає товар через yield return. Повний JsonDocument і список товарів у потоковому шляху не створюються; пам'ять читача залежить від буфера й розміру окремого запису. Сам каталог зберігає додані товари.

CatalogService.ImportAsync споживає потік через await foreach та WithCancellation. Атрибут [EnumeratorCancellation] дозволяє передати токен скасування асинхронному ітератору, зокрема через WithCancellation. await using закриває файл після завершення, помилки або дострокового припинення перебирання. LoadAsync збережено як сумісний метод, який явно збирає потік у список.

Операція не є атомарною: помилка пізнішого запису чи скасування залишає попередні успішно додані товари. Повторний імпорт пропускає їх за Id. Кореневий елемент, відмінний від масиву, відхиляється як DomainException після короткої перевірки початку документа. Пошкоджений синтаксис JSON спричиняє JsonException; помилки вмісту окремих записів — DomainException із номером запису. Тести перевіряють додавання до запиту наступного елемента, отримання першого товару до помилки другого та звільнення файла після помилки.

### Додаткове завдання 2 — зв’язані токени скасування

Консольний імпорт використовує незалежні CancellationTokenSource: userCts для Ctrl+C і timeoutCts для --timeout-ms=N. CreateLinkedTokenSource об’єднує їхні токени; сервіс та імпортер отримують linkedCts.Token і припиняють роботу після сигналу будь-якого джерела. При скасуванні консоль показує причину: запит користувача або вичерпання часу очікування. Якщо на момент обробки активні обидва джерела, повідомлення має пріоритет запиту користувача. Усі джерела звільняються через using, обробник Ctrl+C відписується у finally.

Параметризований тест перевіряє обидва джерела окремо на імпортері, який очікує скасування без доступу до диска. Таймер активується після початку очікування. У сценарії таймауту перевіряється, що timeoutCts скасований, а userCts не скасований; у сценарії користувача — навпаки. В обох випадках перевіряються пов’язаний токен у винятку, порожній каталог і завершення ітератора. Граничне очікування тесту обмежене п’ятьма секундами; точна тривалість спрацювання таймера не перевіряється.

### Додаткове завдання 3 — прогрес імпорту

ImportAsync і StreamAsync приймають необов’язковий IProgress<int>. Core повідомляє числовий прогрес без залежності від консолі, а ConsoleImportProgress у Cli показує рядки «Імпорт: N%». Синхронна реалізація підписника зберігає порядок повідомлень і не залишає відкладених викликів після завершення команди; повторні значення не друкуються.

Сервіс повідомляє 0% на початку й 100% лише після успішного завершення перебирання та перевірки скасування. Проміжні значення JsonCatalogImporter оцінює як частку прочитаних байтів файла, обмежену 99%. Буферизація може випереджати обробку записів, тому це приблизний прогрес читання, а не точна частка доданих товарів. Для малого файла типовий вивід — 0%, 99%, 100%. Повне попереднє читання чи підрахунок записів не потрібні; потокова обробка збережена.

Порожній масив і повторний імпорт лише з наявними Id також завершуються на 100%, оскільки всі дані оброблено. При помилці чи скасуванні 100% не повідомляється. Параметризований тест перевіряє правильний файл, порожній масив, неправильний запис і скасування, діапазон 0–100, незменшення значень, проміжні повідомлення та повторний імпорт.

### Додаткове завдання 4 — покриття тестами

Покриття виміряно coverlet.collector командою `dotnet test --collect:"XPlat Code Coverage" --results-directory tests/coverage`. Усі 18 перевірок пройшли. Вимірювання стосується Core під net10.0: покрито 190 із 839 виконуваних рядків (22,64%) і 52 із 283 гілок (18,37%). Навіть у новому імпортері немає виконаних перевірок фізично порожнього файла та елемента масиву, який не є об’єктом.

Такий обсяг прийнятний для меж цієї лабораторної: тести зосереджені на ключових інваріантах, подіях, вибраних звітах, потоковому імпорті, скасуванні та прогресі. Він не означає повної перевірки всього Core; для повного регресійного набору потрібні додаткові перевірки попередніх компонентів і негативних сценаріїв. Загальне покриття наведене без виключення неперевірених класів із розрахунку.
